# ApplyPilot interface contract

This document is the single source of truth for the interfaces shared by the
Python backend (`src/applypilot`), the Firefox extension (`firefox/`) and the
test harnesses. Every component must conform to it; change it first when an
interface changes.

```
Astra / ChatGPT ──MCP (streamable HTTP or stdio)──► applypilot backend (Python)
                                                     │  FastAPI + worker pool + SQLite
Firefox extension (background) ◄──WebSocket /bridge──┘
        │ browser.tabs / scripting
        ▼
content scripts (adapters.js + dom-engine.js + content.js) in owned tabs/frames
Dashboard / popup (extension pages) ──HTTP /api/*──► backend
```

## 1. Authentication

* Backend binds `127.0.0.1` only by default.
* A random token (`APPLYPILOT_TOKEN`, generated by `applypilot setup`) authenticates
  every channel:
  * WebSocket bridge: `ws://127.0.0.1:<port>/bridge?token=<token>`. The backend
    also rejects any `Origin` that is not `moz-extension://…` (or absent, for
    test harnesses run with `APPLYPILOT_ALLOW_NO_ORIGIN=1`).
  * HTTP API: header `X-ApplyPilot-Token: <token>` (or `Authorization: Bearer <token>`).
  * MCP streamable HTTP: `Authorization: Bearer <token>` **or** the capability URL
    `/mcp/<mcp_token>` (`APPLYPILOT_MCP_TOKEN`, for clients such as ChatGPT that
    cannot send custom headers).
* `GET /api/health` is the only unauthenticated endpoint (returns `{ok, version}`).

## 2. Bridge WebSocket messages

All messages are JSON objects with a `type`.

### Extension → backend

| type | fields | meaning |
| --- | --- | --- |
| `hello` | `version`, `browser`, `owned: [{app_id, tab_id, window_id, url}]` | sent on every (re)connect; lets the backend reconcile tab ownership |
| `result` | `id`, `ok: bool`, `result?`, `error?: {code, message, details?}` | reply to a command |
| `event` | `event`, `app_id?`, `data?` | async notification. Events: `tab_closed`, `tab_navigated` (`data.url`), `user_action` (`data.action` = `resume`/`pause`… from popup — optional) |
| `pong` | `ts` | reply to `ping` |

### Backend → extension

| type | fields |
| --- | --- |
| `command` | `id` (unique string), `app_id` (string, required except for `list_owned`), `action`, `payload` (object), `timeout_ms` |
| `ping` | `ts` |

Exactly one `result` is sent for every `command`. Commands for the same `app_id`
are executed sequentially by the extension (per-application mutex). Commands for
different `app_id`s may run concurrently. A command whose `app_id` has no owned
tab fails with `NO_OWNED_TAB` (except `open`, which creates the tab).

### Error codes

`NO_OWNED_TAB`, `TAB_CLOSED`, `TIMEOUT`, `ELEMENT_NOT_FOUND`, `NO_OPTION_MATCH`,
`DISABLED`, `VERIFY_FAILED`, `NAVIGATION_FAILED`, `CONTENT_SCRIPT_UNAVAILABLE`,
`HOST_PERMISSION_REQUIRED`, `UNSUPPORTED`, `BAD_REQUEST`, `INTERNAL`.

### Actions

Tab-level (handled by the background script):

| action | payload | result |
| --- | --- | --- |
| `open` | `url`, `strategy: "window"\|"tab"` (default window), `active: bool` | `{tab_id, window_id, url, title}` after load completes. Re-uses the existing owned tab if one exists (navigates it). |
| `navigate` | `url` | `{url, title}` after load |
| `wait_ready` | `timeout_ms` (default 20000), `quiet_ms` (default 600) | `{url, title, ready: bool}` — document complete in top frame and no DOM mutations for `quiet_ms` |
| `tab_info` | – | `{tab_id, window_id, url, title, status}` |
| `focus` | – | `{ok, tab_id, window_id, url, title, confirmed, tab_active, window_focused}` (activate tab, focus window, and report verification) |
| `close` | – | `{ok: true}`; releases ownership |
| `screenshot` | `format: "jpeg"\|"png"`, `quality` | `{data_url, width?, height?}` (activates the owned tab in its window first) |
| `list_owned` | – (no app_id) | `{owned: [{app_id, tab_id, window_id, url}]}` |

Content-level (background forwards to content scripts in all frames of the
owned tab, aggregating results; element ids embed the frame id):

| action | payload | result |
| --- | --- | --- |
| `scan` | `include_text: bool` (default false), `max_text: int` (default 4000) | `PageSnapshot` (§3) |
| `fill` | `items: [{field_id, value}]` | `{results: [{field_id, ok, actual?, error?: {code, message}, options?: [Option]}]}` |
| `upload` | `field_id`, `file: {name, mime, base64}` | `{ok, files: [names]}` |
| `click` | `element_id` | `{ok, href?}` (field or button id) |
| `click_text` | `text`, `exact: bool` | `{ok, element_id}` — finds the best visible clickable element whose text matches |
| `click_point` | `x`, `y` (CSS px in the top-frame viewport) | `{ok, tag, text}` — visual fallback, dispatches a click on `elementFromPoint` |
| `highlight` | `element_id` | `{ok, element_id, tag, text}` — briefly outlines the action target for Watch Mode |
| `extract_text` | `max_chars` | `{text, url, title}` (visible text of all frames, top first) |

### Element ids

`"<frameId>:<n>"` where `frameId` is Firefox's frame id (0 = top) and `n` is a
per-document counter stored on the element as `data-ap-id`. Ids are stable for an
element for the life of its document. The backend must re-scan after navigation.

## 3. PageSnapshot

```jsonc
{
  "url": "https://…", "title": "…", "frames": 2,
  "ats": "greenhouse" | "lever" | "ashby" | "workday" | "icims" | "smartrecruiters" | "simplify" | "generic",
  "page_kind": "form" | "job_description" | "login" | "signup" | "verification"
             | "confirmation" | "captcha" | "closed" | "already_applied" | "error" | "unknown",
  "heading": "…",
  "step": {"current": 2, "total": 5, "label": "My Experience"} | null,
  "fields": [Field],
  "buttons": [Button],
  "errors": [{"text": "…", "field_id": "0:12" | null}],
  "captcha": {"present": false, "library_detected": false, "widget_present": false,
              "challenge_blocking": false, "kind": null, "interactive": false,
              "detail": null, "evidence": []},
  "confirmation": {"detected": false, "text": null},
  "signals": {"has_password": false, "has_submit": true, "text_hash": "…"},
  "text": "visible text excerpt (only when include_text)",
  "fingerprint": "hash of url path + heading + field keys"
}
```

`Field`:

```jsonc
{
  "id": "0:12",                // action handle
  "key": "f_ab12cd34",          // stable semantic key: hash(normalized label|name|type|section)
  "frame": 0,
  "type": "text" | "email" | "tel" | "number" | "url" | "date" | "month" | "textarea"
        | "select" | "radio" | "checkbox" | "checkbox_group" | "combobox" | "file" | "password",
  "label": "First Name",        // best human label (label/aria/legend/question text)
  "name": "first_name",         // name/id attribute (may be empty)
  "description": "help text",  // aria-describedby / nearby helper text
  "placeholder": "",
  "section": "Voluntary Self-Identification",  // nearest section heading/legend
  "required": true,
  "disabled": false,
  "value": "…" | ["…"] | true | null,       // current value (combobox: displayed text)
  "options": [{"label": "Yes", "value": "yes", "selected": false}] | null,
  "options_dynamic": false,     // combobox whose options load after typing
  "multiple": false,
  "max_length": 2000 | null, "min_length": null,
  "autocomplete": "given-name" | null,
  "accept": ".pdf" | null,      // file inputs
  "files": ["resume.pdf"],      // file inputs: currently attached names
  "error": "This field is required" | null,
  "hint": "workday:dropdown" | null   // adapter-specific widget hint
}
```

Rules:

* Radio buttons sharing a name/group form ONE field of type `radio` with `options`.
* Several checkboxes under one question form ONE `checkbox_group`; a lone checkbox
  (e.g. consent) is `checkbox` with the checkbox's label.
* Custom widgets (React-select, Workday prompts, Ashby yes/no buttons, aria
  comboboxes/listboxes) appear as `combobox`/`radio`/`select` fields; adapters map
  them.
* Hidden, honeypot (`aria-hidden`, off-screen tiny inputs named like `website`/
  `fax` with `tabindex=-1`) and disabled-by-design inputs are omitted.
* `password` fields are reported (needed for account flows) but values are never
  returned — `value` is `null` for passwords.

`Button`:

```jsonc
{"id": "0:40", "text": "Submit Application", "kind": "submit" | "next" | "back" | "apply"
 | "login" | "signup" | "verify" | "add" | "other", "disabled": false, "frame": 0}
```

### Fill semantics

| field type | value accepted |
| --- | --- |
| text-like / textarea | string (replaces content; React-compatible events) |
| select / radio / combobox | string option label (preferred) or option value. Matching order: exact label, exact value, case/space-insensitive, then unique prefix/contains. Ambiguous or missing → `NO_OPTION_MATCH` with `options`. Comboboxes type the text to load options first. |
| checkbox | boolean |
| checkbox_group | array of option labels (exact set to be checked) |
| date / month | ISO `YYYY-MM-DD` / `YYYY-MM`; engine converts to the input's expected format (native date input, or `MM/DD/YYYY` text when placeholder suggests) |
| password | string; never echoed in results |

After filling, the engine reads the value back; a mismatch → `VERIFY_FAILED` with `actual`.

## 4. HTTP API (dashboard, popup and stdio MCP proxy)

All JSON. All require the token header except `/api/health`.

| method & path | body / query | response |
| --- | --- | --- |
| `GET /api/health` | – | `{ok, version}` |
| `POST /api/pair` | – (no token; requires `Origin: moz-extension://…` and an open pairing window) | `{token, version}` |
| `POST /api/pairing/open` | `{seconds}` | `{open_for_seconds}` |
| `POST /api/manual` | `{url, company?, title?, location?}` | `{application_id, job_id, created, state}` |
| `GET /api/status` | – | `Status` (below) |
| `POST /api/control` | `{action: "start"\|"pause"\|"resume"\|"stop", mode?: "backlog"\|"new_jobs"\|"continuous"}` | `Status` |
| `POST /api/sync` | `{mode?: "backlog"\|"new_jobs"}` | `{fetched, new, updated, closed, queued, checkpoint}` |
| `GET /api/applications` | `q, company, role, state, ats, resume, failure (bool), date_from, date_to, limit, offset` | `{items: [AppSummary], total}` |
| `GET /api/applications/{id}` | – | `AppDetail` |
| `GET /api/applications/{id}/events` | `after_id, limit` | `{events: [Event]}` |
| `POST /api/applications/{id}/action` | `{action: "resume"\|"retry"\|"retry_captcha"\|"skip"\|"open"\|"submit"\|"cancel", note?}` | `AppSummary` |
| `POST /api/applications/{id}/answer` | `{field_key, value, remember: bool}` | `AppSummary` |
| `GET /api/queue` | `limit` | `{items: [AppSummary]}` |
| `GET /api/reasoning` | `status` | `{items: [ReasoningItem]}` |
| `GET /api/logs` | `level, component, application_id, limit` | `{lines: [LogLine]}` |
| `GET /api/metrics` | – | `Metrics` |
| `GET /api/config` | – | `{ready, missing: [], warnings: [], resumes: [...], settings: {...}}` |
| `POST /api/rpc/{operation}` | operation arguments | operation result (used by `applypilot mcp --stdio`) |

```jsonc
  "workers": [{"worker_id": "browser-1", "pool": "browser"|"prep", "status": "idle"|"busy",
               "application_id": "…", "company": "…", "title": "…", "state": "FILLING",
               "activity": "Filling 13 fields", "since": 1730000000.0}],
  "limits": {"browser_workers": 2, "prep_workers": 4},
  "counts": {"QUEUED": 120, "SUBMITTED": 18, ...},
  "queue_remaining": 127,
  "today": {"submitted": 18, "skipped": 2, "ineligible": 5, "needs_user": 1, "failed": 0, "active": 3},
  "needs_user": [{"application_id": "…", "company": "…", "title": "…", "reason": "…",
                  "kind": "captcha"|"missing_fact"|"login"|"verification"|"unexpected"|"review",
                  "instructions": "…", "since": 0.0}],
  "pending_reasoning": 3,
  "bridge": {"connected": true, "last_seen": 0.0, "owned_tabs": 2},
  "config": {"ready": false, "missing": ["candidate.identity.first_name"]},
  "recent_errors": [{"ts": 0.0, "application_id": "…", "message": "…"}],
  "version": "…"

```

`AppSummary`: `{id, job_id, company, title, location, state, state_reason, ats, resume,
domain, simplify_url, application_url, current_url, created_at, updated_at,
submitted_at, attempts, needs_user, worker_id, eligibility_decision, failure}`.

`AppDetail`: `{summary: AppSummary, job: {...}, eligibility: {...}, resume: {...},
answers: [Answer], research: [Research], events: [Event], errors: [Event],
pages: [{url, kind, fingerprint, ts}], submission: {...} | null, metrics: {...}}`.

`Answer`: `{field_key, question, normalized, qclass, field_type, options, required,
limit, value, method, source, confidence, status, page_index, updated_at}` where
`method ∈ {deterministic, fact, preference, eeo, template, reused, generated, user,
default, research}` and `source` explains provenance (fact paths, template name,
memory id, research ids, model call id).

`Event`: `{id, ts, application_id, job_id, worker_id, component, event_type, level,
message, data}`.

## 4b. Implementation notes (additions to the original contract)

* `open` results also include `loaded: bool`; snapshots may include `ats_data` (Simplify page data).
* Fill results may carry `warning` (e.g. text truncated to `maxlength`) and, for comboboxes that
  could not match, `options` with the live option list (`NO_OPTION_MATCH`).
* Field `hint` values: `combobox`, `listbox`, `buttons`, `greenhouse:react-select`, `workday:dropdown`,
  `workday:prompt`, `workday:date-segments`, `ashby:yesno`, `text-date:<format>`.
* `captcha.present` may be true for a vendor library or embedded widget. Only
  `captcha.challenge_blocking` / its compatibility alias `captcha.interactive` (and
  `page_kind: "captcha"`) means a human must act.
* Interactive challenges park the application in `WAITING_FOR_CAPTCHA`. `retry_captcha` performs
  one read-only scan; normal operation does this periodically and resumes automatically. A cleared
  challenge whose resulting page is still login/signup transitions to `ACCOUNT_REQUIRED`, not the
  prior applying state.
* Unattended provider results use strict schema output when supported, followed by application-level
  validation and two repair attempts. Exhausted repairs produce a failed reasoning item plus an
  explicit recoverable `NEEDS_USER` state.
* Background runtime messages for extension pages: `bridge_status`, `bridge_reconnect`, `bridge_user_action`.
* Requests arriving through a reverse proxy/tunnel (forwarding headers present) may only reach `/mcp`.
* Test-only: the jsdom fake browser (`tests/js/fake_browser.cjs`) additionally accepts
  `__test_eval` to simulate a human acting in a page. The real extension has no such action.
